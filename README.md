# Лабораторна робота №3 — Агрегація даних та візуалізація

Deployed URL: https://wuzimoo.github.io/web_tech_lab3/ (запуститься після першого успішного GitHub Pages деплою).

## Опис проєкту
SPA «Web Tech Lab 3» — це дашборд для подій, який отримує дані з JSONPlaceholder та доповнює їх локальною аналітикою. Кожен comment інтерпретується як реєстрація; ми детерміновано генеруємо дати за останні 30 днів, групуємо їх, будуємо графік у Recharts та відображаємо розширену статистику. Розділ імпорту дає змогу підтягувати нових учасників з https://randomuser.me, зберігати їх у `localStorage` та показувати останні 10.

### Що таке аналітика
- 30-денний слід реєстрацій з фільтрами за періодом (7/14/30) та порогом мінімальної кількості.
- Інтерактивний AreaChart (ResponsiveContainer, tooltip, легенда), який миттєво реагує на зміну фільтрів без перезавантаження сторінки.
- Extended stats: total/average, max/min day після застосування фільтрів.

### Що таке імпорт
- Кнопка `Import new participants` отримує 10 користувачів із RandomUser API та зберігає їх у `localStorage` під ключем `importedParticipants`.
- У таблиці відображаються останні 10 записів; є підказка про загальну кількість та кнопка `Clear imported`.

## Техстек
- Vite + React (JavaScript)
- react-router-dom 7
- Recharts 3
- Fetch API для всіх HTTP викликів
- CSS Grid/Flexbox, mobile-first layout без сторонніх UI бібліотек

## Маршрути
| Route | Опис |
| --- | --- |
| `/` | Home — список подій з інфінітним скролом, лоадером та повтором запиту при помилці. |
| `/participants/:eventId` | Participants — коментарі для конкретної події, сприймаються як учасники. |
| `/analytics` | Analytics — графік реєстрацій, фільтри, статистика, імпорт нових учасників. |
| `*` | NotFound — fallback із навігацією назад додому. |

## Фільтри та оновлення графіка
- **Range** (7/14/30 днів): обрізає агреговані дані за останніми N днями.
- **Min count**: прибирає дні з кількістю реєстрацій, що нижча за введений поріг.
- Обидва фільтри змінюють state, що вмикає перерахунок селекторами `useMemo`, графік Recharts перебудовується на льоту.

## Deploy через GitHub Pages
- Workflow `.github/workflows/deploy.yml` збирає застосунок на Node 20 (`npm ci && npm run build`).
- Артефакт `dist/` завантажується через `actions/upload-pages-artifact` та розгортається `actions/deploy-pages`.
- Після першого запуску увімкніть Pages у налаштуваннях репозиторію (gihub-pages environment).

## Виконані критерії
- **Базові:** маршрути, список подій з JSONPlaceholder, завантаження учасників, стани loading/error, адаптивна верстка.
- **Середній рівень:** інфінітний скрол, агрегація реєстрацій з детермінованими датами, графік Recharts у ResponsiveContainer, фільтри, статистика.
- **Просунутий рівень:** імпорт RandomUser, кешування у `localStorage`, лічильник та очищення, Extended stats, GitHub Pages workflow.

## Тест-кейси
1. Відкрити `/` та переконатися, що перші 10 подій з’явилися, а при скролі вниз завантажуються наступні.
2. Вимкнути мережу та спробувати завантажити ще події — відобразиться ErrorState з кнопкою Retry.
3. Зайти на `/participants/1` — має показатися список коментарів, лоадер та повернення до Home.
4. Змінити `:eventId` на неіснуючий (наприклад, 999) — отримаємо порожній список без помилок.
5. На `/analytics` перевірити, що графік показує 30 точок та tooltip/legend працюють.
6. Перемкнути Range на 7 днів — графік та статистика мають відображати лише останній тиждень.
7. Встановити `Min count = 3` — з графіка зникнуть всі дні з меншою кількістю, а min day стане "n/a", якщо масив порожній.
8. Натиснути `Import new participants` — після успіху з’явиться бейдж `Imported!`, таблиця поповниться даними, total збільшиться.
9. Оновити сторінку — імпортовані учасники мають зчитатися з localStorage.
10. Натиснути `Clear imported` — таблиця спорожніє, total стане 0.

## Висновок
Під час виконання лабораторної роботи було реалізовано SPA зі сторінкою аналітики, яка агрегує реєстрації за днями та відображає їх на інтерактивному графіку. Дані з API підготовлено до часової осі, додано фільтри та розширену статистику, а інтерфейс адаптовано під мобільні екрани. Також реалізовано імпорт сутностей із зовнішнього відкритого API із збереженням результатів у localStorage. Проєкт підготовлено до публікації та налаштовано автоматичний деплой через GitHub Pages після push у гілку main.

## Контрольні запитання
1. Які формати даних найзручніші для побудови часових графіків? — Найзручніше працювати з масивами обʼєктів, де є ISO-рядок дати та числове значення; це дозволяє без додаткових перетворень подавати дані у Recharts чи інші бібліотеки. Такі формати легко сортувати, фільтрувати й кешувати.
2. Що таке агрегація даних на рівні API і чому це краще за розрахунки на фронтенді? — Коли сервер повертає вже підсумовані показники (наприклад, кількість реєстрацій на день), клієнт отримує менше даних і менше обчислює. Це знижує навантаження на браузер і прискорює відмальовування графіків.
3. Яка різниця між деплоєм фронтенду (Vercel) та бекенду (Render/Railway)? — Фронтенд-хости оптимізовані під статичні бандли, CDN і швидке кешування, а бекенд-платформи підтримують довготривалі процеси, бази, фон чи cron. Тому SPA можна деплоїти на Vercel/Pages, а API — на Render/Railway.
4. Навіщо у файлі README.md вказувати інструкції щодо npm install? — Це скорочує час онбордингу: будь-який студент або викладач миттєво бачить кроки для запуску та не робить помилок із пакетами. README стає єдиним джерелом правди для локального середовища.
5. Як забезпечити чуйність (responsiveness) для SVG-графіків у React? — Обгорнути графік у контейнер, який вимірює розміри батька (наприклад, `ResponsiveContainer`), та працювати з відсотками ширини/висоти. Тоді SVG автоматично масштабується в межах flex/grid-макету.
6. Які переваги використання декларативних бібліотек візуалізації (як Recharts) перед прямим маніпулюванням DOM через D3.js? — Вони інтегруються з React state, абстрагують розмітку та анімації, тому фокус зміщується на дані та пропси. D3 дає більше контролю, але вимагає ручного керування життєвим циклом і взаємодії з DOM/SVG.
7. Чим відрізняється рендеринг графіків у форматі SVG від Canvas з точки зору продуктивності та стилізації? — SVG легше стилізувати через CSS і воно краще підходить для графіків із малою/середньою кількістю точок, але важче масштабується. Canvas продуктивніший для тисяч елементів, проте вимагає ручного малювання та складніше для інтерактивної семантики.
8. Як підготувати дані, отримані з API, для коректного відображення на осі X у лінійному графіку? — Потрібно нормалізувати дату до ISO-формату, відсортувати записи за часом та впевнитися, що категорії унікальні. За необхідності дані агрегіються по днях/тижнях, щоб уникнути дублювання точок.
9. Для чого використовувати змінні оточення (.env) при деплої проєкту, що працює з зовнішніми API? — Вони дають можливість безпечно зберігати ключі та базові URL, розділяти staging/production і не хардкодити секрети у репозиторій. Це спрощує CI/CD та знижує ризик компрометації токенів.
10. Як реалізувати динамічне оновлення графіка при зміні фільтрів користувачем без перезавантаження сторінки? — Тримати фільтри у React state, а дані для графіку обчислювати через `useMemo` або селектори, які реагують на зміни. Після зміни фільтра оновлений масив миттєво передається в компонент Recharts і графік перемальовується.

## Troubleshooting: push блокується через workflow scope
Якщо GitHub відмовляє у `git push` через відсутність прав на редагування workflow, потрібно розширити скоупи доступу.
- **Варіант A:** виконати `gh auth login --scopes "repo workflow"` і повторити `git push`.
- **Варіант B:** створити PAT з правами `repo` + `workflow`, а потім оновити remote: `git remote set-url origin https://<TOKEN>@github.com/wuzimoo/web_tech_lab3.git` і знову запустити push.
